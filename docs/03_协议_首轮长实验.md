# 首轮长实验协议

## 决策依据

用户已允许长时间本机运行并授权实现。当前已经实现程序、安装 CPU 依赖，通过 15 项测试和五版本短跑。

500 步、单种子的验证集试跑表明：模型能开始学习，尚未接近全部解对；概率回改尚未优于普通生成。详见 `results/pilot/report.md`。因此不扩大模型、不为某一种方法单独调参，而是延长共同训练预算并重复种子，检查短跑结果是否只是训练不足或随机波动。

实测每版 9,475 个参数，试跑峰值内存约 288～292 MiB。模型规模比最初估计更小；启动环境和 PyTorch 运行时占主要内存。原始三种核心对照之外，加入额外计算对照与不回改的软反馈消融。

## 预先固定的配置

- 配置：`configs/cpu_long.json`。
- 输出：`results/long_v1/`。
- 数据：`data/color6.json`，1024 训练题、128 验证题、256 测试题。
- 数据 SHA256：`f7e53ef76871a4d12c67de9f0e4a3b5731ff6c32ce64be00e809546c65bc1abc`。
- 数据长度：6 个待填位置；3 个锚点；3 种颜色。
- 模式：`ar`、`extra_compute`、`hard`、`soft`、`soft_feedback`。
- 种子：0、1、2；共 15 次串行训练。
- 每次 5000 个更新，批次 16；单层、32 维、2 注意力头、前馈宽度 64。
- Adam，学习率 0.001，梯度范数上限 1，无 dropout。
- 每 250 步评估验证集并保存最近检查点；另存验证集表现最好的检查点。
- 检查点选择：首先最大化验证集整题准确率，打平时最小化最终位置交叉熵。
- 每次训练阶段最多 1200 秒，触及时按实际完成度记录，不宣称完成 5000 步。
- 每次完成后用选中的检查点评估测试集；不依据中间测试结果修改剩余版本的配置。
- 不在本套结果出来前扩大数据、改变训练损失或模型、选择性重跑弱结果。

所有版本草稿反馈均断开跨轮梯度，监督目标仅用于损失和统计，不构成前向输入。训练采用模型自己产生的草稿，不使用真实后文。各版本具体差异和公平性边界见 `README.md`。

## 比较顺序

1. `soft` 对 `hard`：概率候选相对确定候选的价值。
2. `hard` / `soft` 对 `extra_compute`：是否不仅仅因为更多计算；三者相同主要网络调用次数和额外监督。
3. `soft` 对 `soft_feedback`：回改是否比单纯概率反馈更有价值；调用预算不同，需结合代价。
4. `ar` 是基础参照，不将其更低计算预算下的结果冒充严格计算匹配。

整题准确率为主指标，位置准确率、约束成功率、旧位置净纠错、计算时间、峰值内存为辅助指标。报告所有种子及均值/标准差，不仅报告最好一次。

## 运行与保护

```bash
.venv/bin/python -m retroar_min.run_local --config configs/cpu_long.json --output results/long_v1 --seeds 0 1 2
.venv/bin/python scripts/report_results.py results/long_v1
```

只使用一个计算线程，单版本独立子进程，无多进程数据加载。开始前可用内存至少 1536 MiB；实验 RSS 超过 1024 MiB 或全机可用内存低于 768 MiB 即停止本实验，不停止其他服务。根据试跑速率估计总耗时约 50 分钟，但不是时间承诺。

中断后先排查 `status.json` 和对应 `console.log`。确认环境与资源正常、代码及数据未改变后，可用同命令追加 `--resume` 从最近完整检查点恢复。源码和数据指纹用于拒绝混合不同协议的运行。

源码运行期间保持不变。输出根目录的 `suite.json` 记录本次训练源码指纹，`status.json` 记录当前运行版本，`summary.json` 逐次更新已完成结果。

## 已完成验证与已知限制

- 数据唯一解、同构去重及训练/验证/测试不重合测试通过。
- 改变监督答案不会改变前向预测，防止答案泄漏测试通过。
- 不回改对照的旧位置保持不变，测试通过。
- 各模式梯度有效，少量题目训练损失下降，测试通过。
- 中断后续训与不中断训练得到一致模型权重，测试通过。
- 低内存拒绝启动、缺少结果文件不认定成功，测试通过。
- 冒烟数据与正式测试集的规范图键无交集；与正式全部数据有 3 道重合，不将冒烟结果作为正式测试。
- Python 静态诊断没有可用的权威 LSP 结果；编译检查和实际测试通过，不能声称已通过完整静态类型检查。
- 单一小型任务、仅 3 个种子，不能据此形成强泛化或普遍性结论。
- 全部生成后统一提交，不能证明流式交付优势。
- 运行成功只代表代码和训练可行；结果不佳时需要分析机制、训练和任务，而非立即宣布所有 RetroAR 方案无效。

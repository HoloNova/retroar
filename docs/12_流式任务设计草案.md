# 设计：流式延迟证据任务（历史草案）

> 2026-09-20 更正：本文件的 `wait_fixed` 在新证据前锁死答案，并非真正“等待后决定”，不能作为主要公平对照；“多算但不用”也不是强基线。以下内容保留作历史记录，**实际收尾实验以 [11_协议_延迟证据.md](11_协议_延迟证据.md) 为准**。草稿温度实验已经结束，未达到事前继续标准；这不能证明所有软信念机制无效。

本文件只是设计，不含实现。目的是给“信息比决策更晚到达”这一原始动机一个可检验的任务，并且**不把模型自己生成的后文冒充成外部证据**。

阅读前需知道两条已确立的结论：

1. 在完整条件可见的小图任务上，整段反复修订（post-hoc）明显强于边生成边修订（阶段 A、阶段 B）。
2. 概率草稿相对确定草稿没有稳定优势；且训练后分布塌缩，需要专门的信念温度实验来公平检验（进行中）。

因此流式任务要回答的不是“修订有没有用”，而是一个更窄的问题：

> **当证据到达时间晚于决策时间时，让未提交的草稿随新证据自动更新，是否优于“不修订但等待同样长的时间”？**

## 1. 为什么必须加“等待但不修订”的对照

如果只比较“能修订的模型”和“立即决定的模型”，任何优势都可能只是**回答得更晚**。所以必须包含一个延迟相同、但一旦决定就不再改变的对照。否则实验只能证明“多等一会儿更准”，这是常识而不是贡献。

## 2. 任务：证据逐步到达的三色图

沿用现有三色图，但把条件拆成按时间揭示的“线索流”。

### 2.1 生成

1. 采样一个 8 个自由点的图，用现有 `solve()` 确认**唯一解**；
2. 随机生成一个线索顺序：3 个锚点 + 若干条边（例如 6～10 条），每条线索在唯一解下都为真；
3. 线索被随机分配到时间轴的若干步；
4. 记录每一步“模型此刻能看到什么”（已揭示的锚点与边）。

关键：**每一步的可观测量都不同**，而唯一解由全部线索共同确定。因此早期决定有真实风险。

### 2.2 时间轴与提交窗口

固定步数 `T = 位置数 + 线索数`（可调）。每步模型做一件或多件事：

- 若有新线索：先更新内部状态；
- 然后为“下一个待回答位置”产生一个候选，放进**未提交窗口**（最多 K 个位置）；
- 任一时刻窗口超过 K 时，最左侧位置被迫提交，之后永不改变。

由此得到三个必须一起变动的量：**窗口大小 K、线索到达时间、提交期限**。这套规则让“拖延”有代价：窗口满了就必须在没有证据的情况下交卷。

### 2.3 变体

| 变体 | 窗口 | 草稿表示 | 是否允许改已进窗口的位置 |
|---|---|---|---|
| `commit_now` | K=0 | — | 立即提交，不修改 |
| `wait_fixed` | K | 确定 | 延迟到第 K 步，但**进窗口时即固定**，之后不改 |
| `window_hard` | K | 确定 | 允许改写窗口内位置 |
| `window_soft` | K | 概率（含信念温度） | 允许改写窗口内位置 |
| `full_info` | K=0 | — | 一开始就看到全部线索（上界，不公平基线） |
| `no_clue` | K | 确定 | 线索从不揭示（下界；确认线索确实有用） |

`wait_fixed` 是这套设计的核心对照：它与 `window_hard` 的**延迟、窗口、计算完全一致**，区别只有“是否允许改写”。这样两者的差值才归因于修订，而不是等待。

### 2.4 计算公平

- 所有变体的每步模型调用次数相同（生成一次 + 修订一次），不允许只有修订版多算；
- `commit_now` 因为不修订会省下算力，应另外给它“多算但不用”的对照（阶段 A 已证明这种冗余计算近似无收益，可作为参考），或允许它用省下的算力做多候选采样（阶段 B 的多候选基线）；
- 延迟必须显式记录：平均提交延迟（从该位置可被回答到实际提交的步数），以及“在证据到达之前就提交的位置比例”。

### 2.5 指标

- 最终整题准确率与约束满足率；
- 平均提交延迟、被迫提交比例；
- 证据到达后发生改写的次数、错改对/对改错；
- **后悔量**：在证据到达前已提交的位置里，最终错误的比例（衡量过早提交的代价）；
- 窗口振荡（同一位置多次来回）；
- 端到端耗时与前向调用数。

### 2.6 事前判读规则

在固定 K（例如 K=4）下，同种子配对比较：

1. `window_hard − wait_fixed ≥ +3 pp` 且 5/5 种子为正 → **修订本身**在信息延迟场景有用（这是本次实验最想要的结论）。
2. `window_hard ≈ wait_fixed` → 在这类任务里“晚点决定”已经足够，修订机制没有独特价值；应把结论写成边界，而不是继续加机制。
3. `window_soft − window_hard` 若在非塌缩温度下稳定为正 → 概率草稿的价值出现在需要处理不确定证据时，这才是 soft 表示真正的用武之地（与阶段 B 的失败形成对照）。
4. 若 `full_info` 明显高于所有流式变体，说明该任务确实依赖完整信息，延迟证据的设计有效；若 `full_info ≈ window_*`，则任务太简单，线索到达时间无关，需要加大难度（更多自由点、更晚的关键线索）。

## 3. 成本更低的先行版本（建议先做）

完整的交错时间轴实现量大、也容易在细节上不公平。建议先做一个**单次注入**的简化版：

1. 模型先用“部分线索”生成完整草稿（窗口内可改，但整段一次性产出，等价于阶段 B 的 post-hoc 流程）；
2. 之后一次性揭示剩余线索；
3. 允许对**尚未提交**的位置再做若干轮修订；已提交的位置冻结；
4. 对照：`wait_fixed`（同样在第 1 步之后才提交，但不再修改）与 `commit_now`（第一部分结束就提交全部）。

这个版本只需要在现有 `posthoc_*` 流程上加一个“线索揭示阶段 + 冻结前缀”，改动小、几天内可跑完，且已经能回答核心问题的一半：**新证据到达后，修订未提交草稿是否优于不修订。**

如果简化版出现正向信号，再投入完整交错时间轴版本。

## 4. 已知的文献风险

以下工作与这个任务高度重叠，实现前必须逐条对照并把差异写清楚：

- **Corrector Sampling / RPT**：固定窗口内重采样已生成的 hard token，用未来 token 作条件。这是“窗口 + 修订”最直接的先例。
- **Projected Autoregression**：连续状态、延迟提交、可变后缀（liquid tail）。
- **Mask-Predict / COrAL**：块内迭代细化。
- **Stream of Revision**：用动作 token 回退并编辑历史。

如果我们的流式任务只是把上述机制搬到“线索逐步到达”的设置里，那么结论必须落在**分析层面**（例如：何时修订优于等待、soft 表示在什么条件下才有用、提交策略与信息到达时间的耦合），而不是落在“首次提出”上。

## 5. 待决问题

1. 任务规模：自由点 8 个、线索 6～10 条是否足够难？需要先测 `full_info` 与 `commit_now` 的差距，确认任务处在可区分区间。
2. 模型是否需要**感知时间**（缺少时间输入时，模型无法知道证据是否还会到来）？最小做法是给每步一个“已揭示线索数/总步数”的编码。
3. 提交是否也由模型决定（学习式 commit gate），还是固定窗口规则？建议先用固定规则，把 commit gate 留作后续变量。
4. 是否需要“线索可被忽略/含噪”的版本？含噪线索更接近真实场景，但会让唯一解与评分复杂化，建议第二阶段再加。
